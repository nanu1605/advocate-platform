# 0011 — Phase 1 API: idempotency, jobs, court-data spend, files and invites

Status: accepted (24 Oct 2026)

## Context
P1 task 5 adds the endpoints in spec §10.2 marked P1. They create jobs the workers run (task 6), spend
court-data money, hand out file URLs and let people join a chamber. §10.1 sets the conventions; this ADR records how
they are met and where the spec left room.

## Decision
**Transactions commit before the response.** FastAPI's default for `yield` dependencies ends them after the
response is sent, so a failed commit could still have answered 200. `UserDb` now uses `scope="function"`. Work that
must follow the commit (enqueueing a Celery task) is registered with `after_commit`.

**Idempotency-Key** (§10.1) is stored in Redis per user, method and path for 24 h. A retry with the same key
gets the first response (`Idempotent-Replay: true`) without running again; a retry while the first is still running
gets 409 `IDEMPOTENCY_IN_PROGRESS` (that marker expires after 2 minutes, so a crash doesn't lock the key). Failed
requests are not stored, so they can be retried. Required on: find-cases, found-cases/add, matters/by-cnr,
matters/{id}/refresh, documents/{id}/complete. Not on case search: it is read-only, rate-limited and served from a
24-hour global cache. Not on order PDF URLs: a GET in the spec; a Redis lock and the global file cache stop double
spending.

**Jobs** are a `jobs` row (synced to the user's devices for progress) plus a Celery task holding only the job id.
`jobs.input` (new jsonb column) keeps what the job was asked to do, so a redelivered task resumes it. Task names live
in `advocate_shared.tasks`; the workers implement them in task 6.

**Court data from the API** goes through `courts.court_data()`: the global daily cap and the organisation's monthly
budget are checked first (§11.8: `COURTDATA_GLOBAL_DAILY_CAP_INR`, `COURTDATA_ORG_MONTHLY_DEFAULT_INR` until plans
exist), and every attempt is written to `provider_calls` and `usage_ledger` with the server connection. With
`COURTDATA_LIVE=0` (local, CI) it calls the synthetic stand-in, never a provider (hard rule: CI makes no live calls).
Case search also has 30 per user per minute and a per-organisation daily cap (`app_config.beta_case_search_daily_cap`,
100, until plans set it in P3).

**Files.** Buckets are private (`documents`, `court-orders`). The API checks access as the user, then signs URLs
with the service key. Download URLs live 5 minutes (§15.5). Upload URLs are Supabase signed-upload tokens, which
Supabase fixes at 2 hours; each is bound to one new path, can't overwrite or read, and the document stays `pending`
until `complete` checks the stored object (size, and that its type matches the declared one; the bucket also
allows only PDF, JPEG, PNG and DOCX) and the worker's malware scan passes. Download links carry a neutral file name
(the document id), never the title, which often names parties. Order PDFs are fetched once per court
order and shared (`court-orders/{cnr}/{sha256}.pdf`); the first fetch is costed to the organisation that asked.

**Invites.** Owners create invite codes (8 characters, no look-alike letters, 7 days). Accepting runs
`public.accept_invite(code)`, a security-definer function, because the invitee can neither read invites nor add
memberships under RLS. Missing, used, expired and wrong-phone codes all return the same `INVITE_INVALID`, and
acceptance is rate-limited, so codes can't be probed. Teams stop at 10 members (F16).

**Deleting a matter** is one call, `public.delete_matter(id)` (security definer, owners and advocates), so the
matter and everything under it (hearings, orders, notes including colleagues' private ones, tasks, deadlines,
documents, board and cause-list rows) are soft-deleted in the caller's transaction.

**Concurrency.** The tracked-case allowance takes a per-organisation advisory lock before counting, so concurrent
adds can't overshoot it; the API's own pre-check takes the same lock. On-demand refresh claims its 6-hour slot
atomically before creating the job. Adding a case by CNR uses `on conflict do nothing`, so two devices adding the same
case get one matter and one fetch. Find-my-cases is limited to 3 new searches per user per day.

**Smaller schema additions.** `matters.court_name` holds the typed court name for manual cases in courts outside the
`courts` list. `hearings_guard` lets the API set `deleted_at` on court-sourced hearings (devices still can't).
Assignee keys to `memberships` clear the assignee when a membership row is deleted, so deleting a user or an
organisation no longer fails while assignments exist.

**Official portal links** point at the national eCourts services, High Court services and Supreme Court sites by
court level. They are links the user opens; nothing fetches them (hard rule 1). The URLs are listed as DRAFT – VERIFY
in `docs/legal-verification.md`.

## Consequences
- Every new error code (e.g. `TRACKED_CASE_LIMIT`, `INVITE_INVALID`, `SEARCH_DAILY_CAP`) needs Hindi and English
  text in the app when its screen is built (tasks 7–11).
- Court-data webhooks (`/webhooks/courtdata/{provider}`) wait for LegalKart keys (Track B).
- Until task 6 lands, jobs stay `queued` and uploaded documents stay `pending`.
